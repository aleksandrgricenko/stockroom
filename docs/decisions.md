# Решения Stockroom

## Остатки и движения

`products.balance` хранит текущий остаток. `movements` хранит журнал с положительным количеством и типом `receipt` или `issue`. Начальный остаток равен нулю. В демоданных ненулевые остатки тоже подкреплены движениями приёмки. Для SKU остаток можно сверить с суммой приходов за вычетом выдач.

`delivery_lines` хранит накопленные количества по строкам заказа. `receipt_lines` хранит принятые и отклонённые количества каждой партии и причину отклонения. В журнале остатков появляются только принятые единицы. Статус поставки вычисляется по сумме принятых и отклонённых единиц. Ноль означает «Ожидается», промежуточное значение означает «Частично обработана», весь заказ означает «Обработана».

## Транзакции и конкуренция

Каждая запись проходит в одной транзакции PostgreSQL с изоляцией `READ COMMITTED`. Приёмка сначала блокирует строку поставки через `FOR UPDATE`, затем читает накопленные количества отдельным запросом. Если одновременно пришла вторая партия, она ждёт блокировку и читает результат уже зафиксированной первой партии.

Приёмка и выдача блокируют строки остатков через `FOR NO KEY UPDATE` перед проверкой и изменением. Для нескольких SKU запрос берёт блокировки в одном порядке по SKU. Другая операция с тем же SKU ждёт освобождения его строки и работает с актуальным остатком. Ошибка в любой строке откатывает приёмку целиком. Ограничения `CHECK` дополнительно защищают остаток от отрицательных чисел, а строки поставки от переприёмки. [Блокировки строк в PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

## Идемпотентность

`POST /api/deliveries/:id/receipts` и `POST /api/issues` принимают UUID в заголовке `Idempotency-Key`. Ключ уникален для обоих маршрутов. В таблице `operations` запрос хранится как канонический текст JSON, исходный ответ хранится в JSONB. В запрос входят тип операции, тело и, для приёмки, ID поставки. При сравнении порядок полей объекта игнорируется. Порядок элементов массива и значения полей сохраняются.

`INSERT … ON CONFLICT DO NOTHING` регистрирует ключ перед изменениями и использует уникальный индекс для координации одновременных запросов. Если ключ уже существует, следующий SQL-запрос видит зафиксированную запись. Совпавший запрос получает исходный HTTP 201 и тело ответа, отличающийся — HTTP 409. Запись ключа и ответ фиксируются вместе с остатками и движениями. После отката не остаётся зарезервированного ключа. Уникальность пары `(operation_id, sku)` также защищает журнал от дублей внутри операции. [Поведение READ COMMITTED в PostgreSQL 17](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).

Конкурентные тесты удерживают строку поставки или остатка дополнительным соединением и проверяют через `pg_stat_activity`, что оба HTTP-запроса ждут блокировок. Затем тест освобождает строку и проверяет ответы, остатки и журнал.
